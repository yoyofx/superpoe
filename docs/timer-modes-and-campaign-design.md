# 计时器三模式与故事开荒计时需求

文档状态：已实现首版。本文档记录已确认需求、实现边界和验证结果；新增章节或日志格式变化时按维护流程更新。

## 三种模式

| 模式 | 用途 |
| --- | --- |
| 异界地图 | 保留现有单次进图停留计时，进入地图开始、离开地图结束 |
| 故事开荒 | 跨区域累计开荒总时间，并分别记录章节耗时 |
| 系统时间 | 独立显示当前系统时间 |

三种模式沿用现有悬浮窗及皮肤、位置、大小设置。系统时间作为正式模式，不再只是表盘的临时切换状态。

## 已确认：故事开荒计时规则

- 手动开始、手动结束一轮开荒；自动识别章节进度用于分段，不用于替代整轮开荒的手动起止。
- 开始后持续累计真实经过时间，只有手动暂停才停止累计。
- 回城、加载、下线、休息及关闭程序均不自动暂停；重启后恢复累计结果，程序关闭期间的时间也计入。
- 手动暂停时，总时间与当前章节时间同时暂停；继续后恢复累计。
- 分别记录第一章、第二章、第三章、第四章、幕间的耗时，幕间合并为一个分段。
- 自动识别首次进入下一章节的有效故事区域（包括该章城镇），结算上一章节并开始下一章节。
- 返回旧章节补任务不会回退分段，其耗时归入当前开荒进度。
- 藏身处、异界地图、角色选择及地图或章节界面切换不推进故事章节；不能仅凭区域带有 `act` 字段就推进。
- 章节计时按已维护的区域映射运行，未知区域不纳入首版业务流程。
- 下线、休息等时间归入当前进行中的章节。
- 手动完成开荒时结算最后一个分段，并停止本轮累计。
- 切换到其他显示模式时，自动暂停当前正在运行的故事开荒计时；切回故事开荒后由用户手动继续，不清空当前轮次，也不删除历史记录。
- 模式切换不会伪造异界地图的离开事件；异界地图仍以游戏日志中的真实区域切换结束，并且不写入故事开荒数据库。
- 中途开始一轮开荒时，从当前已识别的故事章节开始计时；此前章节保持未记录。若当前在藏身处，则沿用最近一次已识别的故事章节。
- “完成”立即结束并保存整轮计时；“重置”立即结束并清空当前整轮计时，不只结束当前章节。

## 界面方向

- 设置面板提供“异界地图 / 故事开荒 / 系统时间”三种模式切换。
- 故事开荒模式的悬浮窗显示总时间和当前章节。
- 设置面板展示各章节用时，以及开始、暂停、继续、完成操作。
- 系统时间模式显示当前时钟，不显示地图或开荒计时状态。
- 模式切换通过计时器右键菜单完成；双击悬浮窗打开当前模式对应的独立窗口。故事开荒窗口提供完整的开始、暂停、继续、重置和完成操作。

当前实现通过计时器右键菜单切换模式，双击悬浮窗打开当前模式的详情窗口；故事开荒详情窗口展示五个章节分段和完整控制按钮。

## 现有实现与技术依据

- 现有异界计时通过监听游戏 `logs/Client.txt` 的新增内容，识别地图进入、离开事件。它记录的是单次停留时间，不判断地图是否刷完。
- 日志解析入口位于 `electron/gameLogTimer.ts`，计时状态和窗口管理位于 `electron/timerWindow.ts`，界面位于 `src/timer/TimerApp.tsx`。
- 异界地图计时继续保存在内存中；故事开荒计时使用 Electron 主进程维护的 SQLite 持久化，因此可在程序重启后恢复未完成轮次。
- 项目自带 `public/pob-lua/Data/WorldAreas.lua`，包含区域 ID 和章节字段，可作为章节识别的数据来源。
- 不能直接把所有区域的 `act` 字段当作故事进度：角色选择等非故事区域同样可能带有章节字段，需要排除，并验证幕间映射。
- 故事开荒的持久化与统计使用本地 SQLite；统计只包含整轮计时和章节分段计时，异界地图计时继续保持现有的内存状态，不写入故事统计数据库。
- 已实现 `electron/campaignTimerStore.ts`、`electron/campaignAreaRules.ts`、计时器 IPC 扩展和故事详情界面；renderer 只通过 preload 接收状态并提交控制操作。

## 区域数据维护与未来章节扩展

### 数据来源与更新边界

- `WorldAreas.lua` 是区域基础数据来源，提供区域 ID、名称、`act`、`isMap` 和 `isHideout` 等字段。日志识别只使用区域 ID，名称仅用于诊断和界面展示。
- 项目通过固定版本的 PoB 上游源码生成 `public/pob-lua/`：更新上游版本或提交后，执行 `npm run pipeline:lua` 重新生成资源，并一并检查资源清单和运行时验证结果。
- 不直接手工修改生成的 `public/pob-lua/Data/WorldAreas.lua`。SuperPoE 自身的章节归类规则应独立维护，避免上游数据重新生成时丢失产品规则。
- 游戏语言变化只会改变 `[SCENE] Set Source` 的显示文本，不应触发章节数据维护；只有区域 ID、区域属性或章节结构变化时才需要检查规则。

### 故事分段归类

区域归类采用“显式特殊规则优先、基础数据辅助”的顺序：

1. 先匹配 SuperPoE 的显式区域规则。当前已确认 `G1_*`、`G2_*`、`G3_*`、`G4_*` 分别对应第一至第四章，`P1_*`、`P2_*`、`P3_*` 统一对应幕间。
2. 对显式规则未覆盖的区域，再读取 `WorldAreas.lua` 的 `act`、`isMap` 和 `isHideout` 等字段，判断它是否属于故事区域。
3. `isMap = true` 的异界地图、藏身处、角色选择、地图界面和其他非故事场景不得推进故事章节。
4. 首版不处理未知或存在歧义的区域；新增区域先完成数据维护和日志验证，再纳入章节计时。

`act` 不能单独决定显示分段。当前三个幕间城镇 `P1_Town`、`P2_Town`、`P3_Town` 都是 `act = 6`，但产品分段仍是“幕间”；未来真正的第六章即使也使用 `act = 6`，也必须通过显式区域规则与幕间区分。

### 新增第五章、第六章的维护流程

当 PoB 或游戏新增章节时，按以下顺序维护：

1. 更新并固定 PoB 上游版本，确认 `WorldAreas.lua` 出现新增区域 ID 和区域属性。
2. 执行 `npm run pipeline:lua`，确认生成的 `public/pob-lua/` 与资源清单一致。
3. 从新章节日志中提取至少一个城镇 ID 和一个普通故事区域 ID。优先记录 `Generating level ... area "区域 ID"`，同时保留场景和加载日志作为辅助证据。
4. 在 SuperPoE 的章节归类数据中增加新区域规则。规则使用区域 ID 或明确的 ID 前缀，不使用本地化名称匹配。
5. 验证从上一章节进入新章节、在新章节内进入普通区域，以及返回旧章节的行为。跳过章节时只推进到实际检测到的最高章节，不为未进入的章节虚构耗时。
6. 更新章节映射测试和本文档中的验证样本，再进行客户端和 Electron 构建验证。

如果新版本只新增普通区域而没有改变章节结构，只需同步 PoB 数据并确认已有归类规则覆盖；如果区域 ID 命名、幕间结构或 `act` 语义变化，则必须增加显式规则并重新验证相关边界。

### 兼容与故障处理

- 新区域需要先加入归类数据并完成验证，未知区域不纳入首版剧情计时流程。
- 区域生成事件重复出现时，以首次进入新的有效故事区域作为章节边界；同一区域重新生成不重复推进章节。
- 旧章节区域可以继续产生日志，但当当前进度已更高时不降低进度。其停留时间按既定规则归入当前开荒进度，具体分配方式在计时状态设计中保持一致。
- 任何语言的 `[SCENE] Set Source` 名称都只作为辅助信息；`(null)`、`(unknown)`、章节界面和“輿圖”等文本不能单独触发章节切换。
- 上游数据缺失、解析失败或区域 ID 无法映射时，保留原始日志事件并记录诊断信息，不阻断异界地图计时和其他功能。

该维护方式的目标是：新增章节主要增加数据映射和验证样本，复用既有日志解析、区域查询和计时状态逻辑；只有日志格式本身发生变化时，才需要修改解析器。

## 故事开荒持久化与统计

### 记录范围

- SQLite 只记录故事开荒模式，不记录异界地图模式的进入、离开或停留时间。
- 系统时间模式不产生计时记录。
- 故事开荒需要持久化整轮总耗时、第一章至第四章和幕间的分段耗时；剧情地图名称、路线和任务数据由独立的指引数据维护，不作为计时统计维度。
- 城镇、普通剧情区域、加载、回城、下线和程序关闭期间的时间，按当前故事规则计入开荒记录；手动暂停期间不计时。
- 剧情地图指引复用故事开荒的当前进度和区域基础数据，显示当前区域、路线进度、下一目标和任务数据；它不参与计时统计。

### 数据结构方向

数据库文件放在 Electron 的用户数据目录中，由主进程统一读写，renderer 通过 IPC 查询和提交操作。首版保持本地单机数据库，不依赖服务端。

- `campaign_runs`：一轮故事开荒，保存状态、开始时间、完成时间和总耗时。
- `campaign_segments`：一轮开荒的五个固定分段：第一章、第二章、第三章、第四章和幕间，保存累计耗时和分段状态。
- `campaign_progress`：保存当前章节和当前区域 ID，用于重启后恢复故事界面和剧情指引位置；不作为历史统计表。
- `schema_migrations`：数据库结构版本和升级记录。

不按每秒写入数据库。章节切换、开始、暂停、继续、完成、重置以及固定间隔保存检查点；恢复时依据最后状态和时间戳补算未暂停期间的时间。完成会保存并结束本轮记录，重置会直接清除当前轮次并结束整轮计时。

### 统计边界

后续统计只读取故事开荒数据，范围为整轮总耗时、第一章至第四章和幕间的分段耗时。区服、游戏版本、角色名、单张剧情地图停留时间等不作为统计维度；异界地图的实时计时不会出现在故事开荒历史和统计结果中。

## 验证记录与后续验证清单

2026-11-15 已完成现有章节和幕间区域的实际日志验证。未来新增第五章、第六章或区域结构变化时，按以下清单对照实际操作提取区域、场景和加载相关事件。

- 记录进入区域前后的 `Generating level ... area`、`[SCENE] Set Source`、`[LOADING SCREEN]` 的实际出现情况、顺序和时间戳，核对区域 ID 与 `WorldAreas.lua` 的映射。
- 实施时以 `Generating level ... area "区域 ID"` 作为章节边界；`[LOADING SCREEN]` 只用于确认加载完成，不作为章节切换依据。
- 首次跨章：确认目标区域属于下一章，并验证上一章结算、新章开始的候选节点。
- 进入新章城镇：确认它能作为有效章节入口，而非被城镇排除规则误忽略。
- 返回旧章节：确认不会回退进度，停留耗时仍归入当前进度章节。
- 打开或切换章节地图界面：确认单独出现的章节或地图场景名称不会被当成跨章。
- 进入幕间：核对实际区域 ID，并确认统一归入“幕间”，不直接使用原始 `act` 数字作为显示章节。
- 未能覆盖的章节与场景明确标为“待验证”，不把已有少量日志样本等同于完整流程通过。

## 实施阶段验证事项

- 验证暂停期间不累计时间，继续后从当前章节恢复；程序关闭期间按既定规则补算未暂停时间。
- 验证直接跳到后续章节时，从实际检测到的当前章节开始，不为未进入章节生成耗时。
- 多轮历史记录的高级查询暂不纳入首版，数据库保留后续扩展空间。
