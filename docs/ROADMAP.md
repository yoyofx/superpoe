# SuperPoE2 产品路线图

> 更新日期：2026-07-31
> 产品方向：面向 Windows 桌面端的 PoE2 离线构筑规划工具。Electron 是唯一应用入口，renderer 继续使用 React、PixiJS、Web Worker 与 WASM 技术栈。

## 1. 路线图目标

SuperPoE2 的目标不是只展示天赋树，而是形成一套可以长期维护的完整构筑工作流：

1. 新建或导入构筑。
2. 编辑天赋、装备、技能和计算配置。
3. 使用原版 PoB 数据与计算逻辑得到可信结果。
4. 在本地可靠保存、备份、恢复和管理构筑。
5. 随 PoB2 与 PoeCharm2 上游更新，一键生成新版本运行资源。

本文描述产品能力和交付顺序。工程历史与细粒度任务继续记录在 [TASKS.md](./TASKS.md)，WASM 计算迁移细节记录在 [pob-wasm-frontend-migration-plan.md](./pob-wasm-frontend-migration-plan.md)。

## 2. 状态定义

| 状态 | 含义 |
| --- | --- |
| 已完成 | 已接入主流程，并经过构建、自动测试或实际界面验证 |
| 可用，待完善 | 主路径可用，但数据覆盖、编辑能力或异常处理尚未达到正式发布标准 |
| 规划中 | 已明确产品目标和依赖，尚未完成实现 |
| 候选 | 是否进入近期版本仍需产品决策 |

## 4. 已确认的后续产品方向

以下十项作为正式产品方向，不再归入远期候选功能：

1. **集市、装备仓库与价格查询**：内嵌国服/国际服官方集市，在页面 listing 注入收藏按钮；市场收藏、PoB 导入、装备界面收藏和游戏内查价共用统一装备仓库、Stat resolver 与官方 Trade Provider。
2. **布局与功能优化**：持续完善构筑中心、编辑工作台、信息密度、自适应布局和高频操作效率。
3. **技能、辅助宝石与伤害分析**：完整展示和编辑技能组，计算单技能与组合 DPS，支持技能伤害排名；怒火、三位一体等全局增益必须作为可控计算条件。
4. **装备提升购买建议**：把仓库和市场候选装备代入当前构筑计算，按 DPS、防御、综合提升和单位价格收益排序。
5. **游戏内 BD 规划器联动**：读取游戏规划器数据，并将 SuperPoE2 方案安全导出到游戏目录。
6. **游戏内查价与提升提示**：在游戏内复制装备后复用统一交易领域查询价格、写入装备仓库，并显示替换当前装备后的 DPS/防御变化。
7. **伤害构成解释**：拆解基础伤害、附加、转化、gain、increased、more/less、暴击、暴伤、速度、敌人减伤等组成，指出可提升方向。
8. **防御构成解释**：拆解生命/护盾、抗性、护甲、闪避、格挡、减伤、承伤转化、恢复等组成，指出防御短板。
9. **编辑后实时提升提示**：修改天赋、属性节点、装备、技能或全局条件后，显示相对上一次稳定结果的 DPS 和防御变化。
10. **双构筑比较**：导入另一套 BD，在统一计算条件下比较伤害、防御、资源、天赋、装备和技能组成，并给出差异提示。

这些方向的依赖关系如下：

```text
集市页面 + 游戏内查价 ── 共享 Session / TradeProvider / TradeStatResolver
             │
             └────────────── 统一装备仓库 ── 候选比较与构筑装备 Adapter

布局与统一构筑模型
├── 技能/辅助宝石编辑 ── 可信 DPS 与全局增益计算 ── 伤害/防御构成解释
├── 天赋/装备/技能编辑 ── 前后计算快照 ────────────── 实时提升提示
├── 统一装备仓库/价格查询 ┐
│                       ├── 装备提升建议 ── 游戏内查价与提升提示
└── 装备编辑与计算 ─────┘

统一构筑模型 + 统一计算条件 ── 双构筑比较
Electron 文件能力 ─────────── 游戏内 BD 规划器导入/导出
```

## 5. 后续里程碑

路线图使用依赖顺序而不是固定日期。每个里程碑完成后都应形成一个可独立验收的版本。

### M0：集市、统一装备仓库与共享交易基础（P0）

目标：优先形成可实际使用的国服/国际服集市工作流，并为页面收藏、PoB 导入、装备界面收藏和游戏内查价建立唯一的数据与查询基础。

详细方案见 [`marketplace-browser-design.md`](./marketplace-browser-design.md)、[`market-subscription-design.md`](./market-subscription-design.md)、[`currency-market-design.md`](./currency-market-design.md) 与 [`price-check-design.md`](./price-check-design.md)。官方集市、实时监控和查价共享交易基础；第三方通货行情保持独立只读 Adapter 与缓存，只向其他模块提供经过归一化的汇率快照。

**当前实现状态（2026-08-01）**：M0 应用侧能力已接入，包括双区服内嵌浏览器、隔离 preload 收藏按钮、官方 Fetch 校验、统一多来源装备仓库、搜索保存与恢复、官方 Live WebSocket、突发机会处理、游戏窗口识别、提示音和置顶机会窗口。保存的搜索、购买目标和机会中心已拆分为独立领域与 UI；旧监控状态会迁移为独立目标，Live Fetch 的完整装备快照、批次和词缀直接落盘。仍需在用户实际 Electron 登录分区中完成双区服、断网/限流、DPI、多显示器和长时运行 smoke test。

- 完成 `WebContentsView` 双区服集市入口、导航、边界、模态框遮挡、DPI、错误状态和安全 allowlist。
- 内嵌集市、认证窗口和查价 API 共用 realm persistent session；Cookie 原文不得进入 renderer、仓库或日志。
- 使用隔离 market preload 和国服/国际服 DOM Adapter，在新版 listing 卡片注入轻量收藏按钮；Adapter 失效时降级为原始官网。
- 页面按钮只发送 `realm + queryId + listingId + sourceUrl`；主进程调用官方 Fetch 并校验为可信 `TradeListingView` 后才允许入库。
- 建立共享 `TradeReferenceDataCache`、`TradeStatResolver`、`OfficialTradeProvider`、限流器和 query builder；运行时数据只来自对应 realm 官方接口。
- 建立 `EquipmentLibraryRepository`。仓库装备是主体，`market-favorite`、`pob-import`、`equipment-favorite`、`price-check` 和 `manual` 是可并存来源。
- 仓库词缀同时保存原始文本、结构化观察值和带 realm/catalog hash 的 Stat resolution；例如 `explicit.stat_3299347043` 只能作为可重新验证的解析快照，不能作为装备永久主键。
- 同一装备多来源幂等合并；取消一个来源不误删其他来源、目录、标签或备注；市场下架只更新来源状态并保留装备快照。
- 提供仓库侧栏和独立仓库界面，支持全部装备、市场收藏、PoB 导入、装备收藏和查价记录等来源视图，以及目录、标签、备注、归档和来源页。
- 支持从仓库装备和当前构筑装备生成同一 `TradeSearchForm`，显示对应 realm/赛季的官方挂牌结果。
- 先完成搜索收藏可用化：严格识别官方搜索页，持久化 realm/leagueId/searchCode/canonical URL，使用项目内表单保存并支持重复检测、条件更新、目录维护和稳定排序。
- SuperPoE2 生成的查询保存经过校验的 query snapshot；官方页面只在请求与导航可安全唯一关联时保存查询体，否则明确降级为 code-only。搜索码失效时自动重新 Search，或引导用户用当前搜索更新。
- 将保存搜索启用为官方 Trade2 Live WebSocket 购买目标，支持优先级、暂停、完成、断线恢复和去重；详细方案见 [`market-subscription-design.md`](./market-subscription-design.md)。
- 实现有界 Opportunity Engine：合并瞬时大量 listing、有限批量 Fetch、校验有效性、按目标优先级/新鲜度/公平性选择少量重点候选，不把原始结果洪泛到游戏窗口。
- 复用查价器的 `GameWindowService` 识别游戏窗口和客户端 realm；游戏前台时使用单一机会面板帮助用户判断并主动“尝试前往”，不承诺 listing 仍有效或交易成功。游戏未运行/后台时只记录，不使用系统通知。
- 不后台监控价格，不自动私聊、购买、翻页或绕过验证。
- 在交易中心增加只读“通货行情”Tab：国服批量读取 poecurrency.top，国际服批量读取 poe2scout；使用稳定主表和来源特有详情区，展示来源、赛季、更新时间、缓存与数据质量，不提供收藏、监控或交易动作。

**完成标准**：双区服官方集市可以稳定浏览；新版 listing 卡片可以收藏到统一装备仓库；PoB 导入和装备面板收藏可写入同一仓库并保留多来源；仓库或剪贴板装备通过同一 resolver 和 Provider 生成可信查询；搜索收藏能够去重、更新、恢复并可靠驱动购买目标；购买目标可以稳定消费官方 Live 接口，大量瞬时命中不会造成请求/声音/窗口洪泛，游戏前台时用户能看到经过基础校验和排序的少量机会并主动尝试藏身处；页面 Adapter 或机会面板失效不会影响官网、仓库和查价 API。

### M1：GitHub Release 自动构建与附件（P0）

- [x] 新增 GitHub Actions 发布工作流：仅在 GitHub **Publish release** 时触发（`release: published`），不响应本地 `git tag` push；另支持手动 `workflow_dispatch`。
- [x] 发布构建前用 Release Tag 版本写入 `package.json`（界面版本从 `package.json` 读取，不再写死测试期望）。

目标：先把当前第一版界面打磨成稳定工作台，并确保用户编辑数小时的构筑不会因为清理缓存、升级应用或误操作而丢失。

- 保证常用桌面窗口尺寸连续自适应，不要求用户使用指定分辨率。
- 将命名构筑从 `localStorage` 迁移到 Electron `userData/builds/`。
- 推荐每个构筑一个 JSON 文件，另用轻量索引保存排序、来源和最近打开时间。

- 增加导出备份和批量恢复，文件格式带 `schemaVersion`。
- 构筑中心补齐装备数量、技能数量和最近打开时间的可靠统计。
- 增加保存、迁移、损坏文件和磁盘写入失败测试。

**完成标准**：核心流程在常用桌面窗口下无重叠和不可达操作；升级应用和重新安装同版本后构筑仍可恢复；异常退出最多丢失最后一次自动草稿间隔内的修改。

### M3：统一构筑模型与可编辑装备/技能（P0）

目标：从“展示导入的 PoB XML”升级为“真正编辑完整构筑”。

- 建立前端统一 `BuildDocument`，集中管理 Tree、Items、Skills、Config 和 Notes。
- 导入 PoB Code 后只解析一次，不再由装备页和技能页各自重复解码 XML。
- 所有编辑操作更新同一构筑模型，并能无损重新导出 PoB Code。
- 装备页支持装备组、武器组、槽位替换、删除和基础物品编辑。
- 装备孔支持 Rune、Soul Core、Idol 添加、移除和顺序调整。
- 技能页支持技能组增删、启用、主技能选择、辅助技能增删、等级、品质和变体。
- 修改装备和技能后统一进入未保存状态，并使计算结果失效。
- 对未知 XML 字段采用透传策略，避免导出时破坏新版 PoB 数据。

**完成标准**：导入一个完整 PoB 构筑，编辑天赋、装备和技能后重新导出，原版 PoB 能正常载入且未编辑数据不丢失。

### M4：技能伤害、全局增益与计算可信度（P0）

目标：让技能与辅助宝石展示、DPS 排名和全局增益开关成为可用于判断 BD 的可信功能。

- 完整展示主动技能、辅助宝石、技能组、武器组、等级、品质、变体、启用状态和触发关系。
- 计算每个技能组的单次命中、持续伤害、攻击/施法频率、单目标 DPS 和 Full DPS。
- 对当前构筑中的技能组提供 DPS 排名，并显示排名采用的敌人、配置和增益条件。
- 支持候选辅助宝石逐个代入计算，按 DPS 增量、适用性和冲突条件排序。
- 建立统一的全局增益/条件模型；怒火、三位一体、球、感电、暴露、诅咒、敌人状态等开关不得散落在 UI 层。
- 每个增益开关显示当前值、来源、是否满足条件及对结果的影响，避免默认暗中启用。
- 增加伤害构成模型：基础伤害、点伤、伤害转化、gain as extra、increased、more/less、攻击/施法速度、命中、暴击率、暴击伤害、穿透、抗性和敌人承伤。
- 增加持续伤害、异常状态、触发技能、召唤物数量、技能阶段和有效覆盖率的独立说明。
- 增加防御构成模型：生命、能量护盾、魔力承伤、抗性与最大抗、护甲、闪避、格挡、减伤、承伤转化、避免、恢复和有效生命池。
- 每个组成项显示基础值、来源、叠加方式、当前贡献和受影响的最终指标，不能只展示一条无法解释的最终 DPS。
- 拆解数据优先来自 PoB Lua 的计算输出、modDB 和 breakdown；前端只负责结构化展示，不另写一套近似公式。
- 同时保存“上一步自动快照”和“用户固定对比基线”；修改天赋、装备、技能或 Config 后，增量计算并显示 DPS、防御和资源变化。
- “上一步”用于解释刚修改的单个节点、装备或技能；“固定基线”用于查看一轮连续调整后的累计提升。
- 提升提示同时显示正向和负向结果，并区分“未重新计算”“计算条件变化”和“构筑内容变化”。
- 将 worker API 收敛为稳定的 `PobEngineClient`，支持初始化、加载构筑、增量更新、计算和崩溃恢复。
- 让 worker 持有构筑实例，避免每次计算重新装载全部 Lua 与 XML。
- 建立代表性 parity fixtures：职业、升华、武器组、属性节点、召唤物、持续伤害、触发技能和多技能 Full DPS。
- 与原版 PoB/LuaJIT 对比 Str、Dex、Int、Life、Mana、ES、抗性、命中、暴击、速度和 DPS。
- 整数和枚举字段要求完全一致；浮点字段明确容差并输出差异报告。
- 实现核心 Config：敌人等级与状态、距离、球数、技能阶段、是否 Boss、条件开关。
- 计算页增加最后计算时间、警告、缺失条件、错误来源和上次结果差异。
- 完成后移除产品路径中的 Fastify/LuaJIT fallback，旧后端仅保留为开发对照工具或移入独立目录。

**完成标准**：约定的回归构筑全部通过 parity 检查；技能 DPS 排名可解释且使用同一组计算条件；切换怒火、三位一体等全局增益后结果与原版 PoB 一致；任一天赋或装备变化都能给出可复算的伤害与防御差异。

### M5：装备提升与购买建议（P1）

目标：把“市场上能买到什么”与“换上后提升多少”连接起来，给出可解释的升级建议。

装备事实、物品面板、完整构筑收益和 Agent 输出的统一口径见 [`equipment-analysis-agent-spec.md`](./equipment-analysis-agent-spec.md)。

- 从当前装备槽位、角色等级、属性需求和预算生成候选查询。
- 将候选物品临时代入 `BuildDocument`，通过同一 PoB worker 重新计算，不修改用户当前构筑。
- 分别计算主技能 DPS、Full DPS、生命、能量护盾、护甲、闪避、抗性、资源和属性需求变化。
- 提供 DPS 提升、防御提升、综合提升、价格、每单位货币收益等排序模式。
- 支持锁定必须保留的词缀、抗性下限、属性需求、装备类型、预算和负面变化容忍度。
- 推荐结果必须解释主要增益来源和代价，例如“DPS +8.4%，但火抗 -21%”。
- 对计算条件、价格时间、缺失词缀和不确定结果做醒目标记，禁止输出伪精确结论。
- 支持将候选装备加入比较列表，用户确认后再写入当前构筑。
- 用户实际更换装备后，在装备槽、顶部状态和计算页同步显示相对上次基线的 DPS/防御变化。
- 提升详情可以继续展开到伤害与防御构成，说明变化来自点伤、inc、more、暴击、暴伤、抗性、生命或其他具体组成。

**完成标准**：对一个指定槽位，能从真实市场结果中生成可复算、可解释、满足预算和约束的升级列表。

### M6：游戏内查价器与构筑提升浮层（P1）

目标：用户在游戏中查看装备时，通过明确的主动操作获得价格和替换后的构筑变化，不需要切回完整工作台。

- 推荐使用“游戏内复制物品文本 + 可配置全局快捷键 + Electron 浮层”的方式获取装备，不读取游戏内存、不注入进程、不分析网络包。
- 服务器统一读取全局默认值；解析剪贴板物品文本的语言、底材、稀有度、词缀、孔位和需求，赛季从对应区服官方列表选择。
- 调用 M0 建立的共享 `TradeProvider` 和 `TradeStatResolver` 查询价格，显示价格区间、样本数量、来源和更新时间。
- 将物品临时代入当前激活构筑和对应装备槽，调用与 M5 相同的增量计算流程。
- 浮层显示主技能 DPS、Full DPS、生命、护盾、抗性、护甲、闪避等关键变化，并标记属性或抗性不满足。
- 支持固定/取消固定、切换目标槽位、展开详细构成、打开交易页面和加入候选列表。
- 浮层默认不抢夺游戏键盘焦点，不遮挡关键区域，并允许设置位置、透明度、缩放和快捷键。
- 增加剪贴板权限、隐私说明、请求限流和离线状态；未查询时不上传物品文本。
- 发布前确认游戏服务条款和允许的工具边界，任何不确定能力都默认关闭。

**完成标准**：在游戏中主动复制一件装备后，可以看到可信价格和相对当前构筑的 DPS/防御变化；关闭浮层不会影响游戏输入。

### M7：游戏内 BD 规划器联动（P1）

目标：让 SuperPoE2 构筑可以安全进入游戏内规划器，同时保留原文件和版本兼容信息。

- 先确认游戏规划器的文件格式、版本字段、默认目录、编码方式和游戏更新后的兼容策略。
- 将规划器解析/生成做成独立模块，不与 PoB Code 或 SuperPoE2 JSON 格式混用。
- 支持从游戏目录读取规划器方案，并在导入前显示职业、版本、节点数和冲突预览。
- 导出前显示目标路径、将写入的方案和文件差异，不直接静默覆盖。
- 写入时使用临时文件加原子替换，并自动备份原规划器文件。
- 游戏运行中或文件被占用时停止写入并提示用户关闭相关界面。
- 设置页允许选择或自动检测游戏目录，并保存多个客户端路径。
- 游戏版本不兼容时只允许导出副本，不覆盖当前规划器文件。

**完成标准**：在受支持游戏版本中，导出的方案可被游戏规划器读取；任何失败均能恢复写入前文件。

### M8：双构筑比较与天赋高级能力（P1）

目标：支持导入另一套 BD 做可解释比较，同时补齐深度玩家高频使用的天赋规划能力。

- 将另一套 PoB Code、WeGame 构筑或 SuperPoE2 JSON 作为只读比较构筑导入，不覆盖当前编辑构筑。
- 比较前统一游戏版本、敌人类型、技能阶段、怒火/三位一体等全局增益和其他 Config；条件不一致时禁止直接给出优劣结论。
- 展示伤害构成对比：基础伤害、点伤、inc、more、gain、速度、暴击、暴伤、穿透、技能数量和 Full DPS。
- 展示防御构成对比：生命/护盾、抗性、护甲、闪避、格挡、减伤、恢复和有效生命池。
- 展示天赋、装备、技能、属性需求和资源差异，并允许定位到具体节点、槽位或技能组。
- 根据差异生成“对方高在哪里、代价是什么、哪些组成可迁移”的提示，不把相关性描述成确定因果。
- 补齐 Jewel radius、影响节点、范围显示和珠宝效果计算。
- 补齐 Mastery 数据、选择 UI、导入导出和计算联动。
- 支持多个 Spec/天赋方案，并能在同一构筑内切换。
- 支持当前方案与另一方案比较：点数变化、属性变化、装备变化和 DPS/防御变化。
- 提供路径成本、最短路径和取消节点后的影响预览。
- 搜索增加类型、属性、升华和分配状态过滤，但保持即时响应。

**完成标准**：当前构筑可以与另一套导入 BD 或同构筑另一方案比较，并在统一条件下清楚解释伤害、防御、天赋、装备和技能差异。

11. 价格查询和装备增量计算都稳定后，实施 M5 装备提升购买建议。
12. 用 M0 的 Provider、resolver 和仓库实现 M6 游戏内剪贴板查价浮层，不开发第二套查价逻辑。
13. 独立研究游戏规划器文件格式与目录，拿到真实样本后实现安全导出。
14. 在统一 Config 和游戏版本后实现双构筑比较，避免比较结论被不同计算条件污染。

## 8. 每个里程碑的共同验收要求

- `npm run build` 通过。
- 正式发布须在 GitHub 上 Publish Release，并由 Actions 生成可校验附件；禁止用开发机手工产物替换。
- 非 Lua 长时测试全部通过；计算相关测试单独运行并设置明确超时。
- Electron 开发模式与打包后的桌面应用均无新增 console error。
- 关键流程至少覆盖一次实际界面回归，不只验证函数测试。
- 不修改 `upstreams/` 中的上游文件；运行时生成资源提交到 `public/`。
- 新功能不依赖 Fastify 后端才能运行，WeGame 外部转换除外。
- 数据格式变更必须包含 `schemaVersion`、迁移和回滚策略。
- 所有破坏性操作必须确认，保存和计算必须有明确成功/失败反馈。
- 市场价格必须标明服务器、赛季、来源和更新时间，不能把缓存价格显示成实时价格。
- 装备推荐必须可以复算，并同时显示收益、损失、预算和计算条件。
- 写入游戏目录前必须预览、备份并采用可恢复写入流程。
- 伤害与防御拆解必须能追溯到 PoB 计算数据，不能由 UI 根据最终值反推。
- 所有前后提升和双构筑比较必须使用相同版本与 Config，并展示基线时间。
- 游戏内浮层只响应用户主动复制/快捷键，不读取内存、不注入游戏、不自动执行交易操作。

## 9. 需要确认的产品决策

以下默认建议可直接作为实施基线，也可以由产品方向调整：

1. **应用平台**：只支持 Windows Electron 桌面应用，不提供独立浏览器版入口。
2. **保存格式**：建议每个构筑一个可读 JSON 文件，索引损坏时仍能扫描恢复；不优先引入 SQLite。
3. **首个稳定版范围**：建议必须包含天赋、装备、技能的基础编辑和可信计算，而不是只读装备/技能。
4. **计算标准**：建议以选定回归构筑的关键指标与原版 PoB 一致为发布门槛，而不是要求所有 Lua 内部状态逐位一致。
5. **WeGame 导入**：建议保留 PoE2DB 外部依赖，并在失败时允许用户手动粘贴 PoB Code，不尝试模拟网页。
6. **多语言优先级**：建议简体中文和英文作为发布阻塞项，繁体中文和韩文保持可用但允许较低覆盖率。
7. **DPS 排名范围**：建议第一阶段只比较当前构筑已有技能组和候选辅助宝石，不直接做全服玩家排行榜。
8. **市场数据源**：国际服和腾讯国服都使用各自官方 Trade2 API；Stat、物品、过滤器与赛季数据按区服隔离并只缓存官方响应，不依赖 Xiletrade。
9. **装备建议目标**：建议先做“指定槽位 + 指定预算”的候选排序，不在第一版做全身自动配装。
10. **游戏规划器**：实现前需要提供或采集一个游戏生成的规划器文件样本和实际目录，先验证格式再设计写入接口。
11. **游戏内查价交互**：建议采用复制物品文本后按快捷键弹出浮层；需要确认是否符合你预期的使用方式。
12. **提升基线**：建议同时提供自动“上一步”和手动“固定基线”；界面默认显示上一步变化，并允许切换查看累计提升。
13. **双 BD 比较**：建议第一版由用户选择主技能和统一 Config，不做系统自动猜测两个构筑的对应技能。
